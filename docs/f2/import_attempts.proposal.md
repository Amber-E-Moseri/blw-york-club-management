# Import attempts: durable identity (PROPOSAL, requires approval before implementation)

**Status: not implemented. Not a migration. Approval is required before it is written to `supabase/migrations/`.**

## Why a migration is needed

The current import identity is held in the browser (`sessionStorage`, per user, per tab). It survives a page reload but not
a closed browser, a different browser, or a second device. A user who closes the tab and re-uploads a corrected file starts
a new import. Rows already written are then written again. Only the database can make that exactly-once across sessions, so
the record of what an import has written must move to the database. That needs new tables and a change to the batch function.

## What the browser implements now (no migration)

- Rows are matched by content, so reordering, inserting and removing rows neither duplicates nor drops anything within one
  attempt.
- A written row whose content changed at its position is held, not written, until the user explicitly imports it as new.
- A retry of the same attempt writes nothing twice, through the server's idempotency keys.
- An intentional new import starts a new attempt only after the previous one finished, or after "Start a new import".

## Proposed migration: `100_import_attempts.sql` (number to be confirmed; 099 is reserved for N1 signup linking)

Tables (owner `postgres`, RLS on, no direct grants to API roles, mirroring the identity audit tables):

```sql
CREATE TABLE public.import_attempts (
  id           uuid PRIMARY KEY,                      -- generated by the client, one per logical import
  logged_by    uuid NOT NULL REFERENCES public.profiles (id) ON DELETE RESTRICT,
  status       text NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'finished')),
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz
);

CREATE TABLE public.import_attempt_writes (
  attempt_id   uuid NOT NULL REFERENCES public.import_attempts (id) ON DELETE RESTRICT,
  fingerprint  text NOT NULL,                         -- content fingerprint of the row as written
  position     int  NOT NULL,                         -- file position when written (for the held-row rule only)
  contact_id   uuid NOT NULL REFERENCES public.contacts (id) ON DELETE RESTRICT,
  written_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (attempt_id, contact_id)
);
```

The batch function `submit_contacts_batch` gains an optional `p_attempt_id`. In the SAME row subtransaction that writes the
contact, its tags and its follow-up, it inserts the `import_attempt_writes` row. A replayed row is detected by the existing
idempotency key and writes nothing. Reads of the open attempt go through a definer RPC `get_open_import_attempt()` that
returns only the caller's own attempts.

## Decisions needed before implementation

1. Approve the two tables and the optional `p_attempt_id` on the batch function.
2. Decide the retention of `import_attempts` rows (for example, keep finished attempts for audit).
3. Decide whether a staff member may see another user's open attempt (proposed: no; only the importer).
4. Confirm that held-row decisions are part of the attempt record (proposed: yes, as `finished` only when no row is held).

## Test plan (to be run on disposable databases once approved)

- Retry in a new session (new browser): the open attempt is read from the database, and nothing is written again.
- Corrected file after a closed browser: only new rows are written; tags and follow-ups are written once per contact.
- Two attempts by two users with identical content: both written, neither sees the other's attempt.
- Post-state for `contacts`, `contact_tags`, `contact_follow_ups` and `import_attempt_writes` after each step.
